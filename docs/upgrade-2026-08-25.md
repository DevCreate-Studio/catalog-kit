# Upgrade inventory: UCP 2026-04-08 → 2026-08-25

Everything in this kit is pinned to UCP release **2026-04-08**. UCP has since tagged
**[v2026-08-25](https://github.com/Universal-Commerce-Protocol/ucp/releases/tag/v2026-08-25)**
(plus a moving Draft on `main`). This page is the standing inventory of what that
release changes for us, where our pins live, and the order to flip them in —
cross-checked against the [UCP upgrade planner](https://ucp.new/tools/upgrade-planner)
and verified against the live endpoint.

## Do not flip yet

Two live checks (2026-08-30) say the upgrade is **preparation, not action**:

- Shopify's Global Catalog endpoint still negotiates **2026-04-08** — a live
  `search_catalog` call returns `x-shopify-ucp-mcp-api-version: 2026-04-08` and
  `ucp.version: "2026-04-08"` in the body.
- Shopify has not published a 2026-08-25 sample agent profile
  (`shopify.dev/ucp/agent-profiles/2026-08-25/…` → 404), while the ucp.dev
  2026-08-25 schema/spec URLs (`schemas/shopping/catalog_search.json`,
  `schemas/shopping/catalog_lookup.json`, `services/shopping/mcp.openrpc.json`,
  `schemas/profile.json`) all resolve.

So the spec is out but Shopify's implementation hasn't moved. The planner's own
checklist agrees: keep production negotiation on the current dated release, run
dual-version validation, and roll out with an older-version fallback. When
`pnpm probe` starts reporting a newer `x-shopify-ucp-mcp-api-version`, run the
[flip checklist](#flip-checklist) below.

## What 2026-08-25 changes for this kit

The kit implements only the **Catalog** surface (search / lookup / get_product)
plus profile hosting. Most of the release's breaking changes — buyer consent,
cart ID omission, fulfillment config, payment credentials/constraints/namespaces —
are Cart/Checkout/Payments contracts we never touch. What's left:

**Affects us (act at flip time)**

- **Common schema relocation (breaking, schema graph).** Shared primitives
  (price, amount, pagination, message, …) move from `/schemas/shopping/types/*`
  to `/schemas/common/types/*`, and the profile schema moves from
  `schemas/discovery/profile.json` to `schemas/profile.json`. We don't resolve
  `$ref`s at runtime (zod schemas are hand-written from fixtures), so impact is
  confined to the dated URLs in `profile/agent-profile.json` and docs. Refresh
  the whole graph; don't rewrite individual `$ref` strings.
- **Independent capability versioning + namespace authority binding (breaking,
  profile).** Capability versions negotiate independently of the root protocol
  date, and platforms verify that a capability's `spec`/`schema` origins are
  controlled by the authority in its reverse-DNS name. Our profile already
  passes the authority check (`dev.ucp.shopping.*` → ucp.dev,
  `dev.shopify.catalog.global` → shopify.dev), but at flip time each capability
  entry's `version` must be set to what that capability actually ships as — not
  blanket-bumped to the root date.
- **`quantity_unit` on variants (additive, catalog response).** Variants can
  carry `{unit, scale, increment, display_text}` describing fractional sale
  units; a related change caps integer quantities at 2^53−1 and adds a
  `unit_price` comparator. Our lenient `.passthrough()` schemas already survive
  it. Worth adding as typed optional fields in `schemas/responses.ts` and
  rendering in the demo (price-per-unit display) once live.
- **Catalog fulfillment availability (additive, catalog response).**
  `products[*].variants[*].fulfillment` can advertise shipping/pickup before
  checkout, with method types as **open strings** (shipping/pickup remain
  well-known) and optional location context. Same treatment: passthrough today,
  typed + rendered later; tolerate unknown method strings from day one.
- **`actions` and `policies` primitives (additive, all responses).** Responses
  may carry extension-defined out-of-band actions and structured policy
  snapshots. Nothing breaks (passthrough), but if we ever surface them, unknown
  action types need an explicit unsupported-action fallback rather than silent
  success.

**Not applicable (catalog-only kit)**

Profile `signing_keys` → `keys` (we publish no keys), buyer consent map, cart ID
omission, fulfillment description/config restructure, payment namespace moves,
request constraints, card-credential deprecation, split payments, payment
terms/3DS, loyalty, location capabilities, identity linking.

## Flip checklist

Run when Shopify's endpoint reports the new version (`pnpm probe --json`):

1. `packages/catalog-client/src/endpoints.ts` — bump `UCP_SPEC_VERSION`.
2. `profile/agent-profile.json` — bump `ucp.version`, per-capability versions
   (individually — see above), and all dated ucp.dev/shopify.dev URLs; confirm
   each new URL resolves.
3. `apps/web/lib/env.ts` + both `.env.example` files — point at the new Shopify
   sample profile once it exists.
4. `pnpm probe --json` → update `docs/probe-findings.md` (table + verified date);
   re-verify the API-gotchas list in `AGENTS.md` against the report.
5. `pnpm fixtures` → `pnpm test` (fixtures re-recorded on the new version).
6. `schemas/responses.ts` — add typed optional `quantity_unit`, `unit_price`,
   `fulfillment`, `actions`, `policies` fields; render `quantity_unit` and
   fulfillment availability in the demo where useful.
7. Sweep the dated version/URLs in `docs/` (step 4 covers probe-findings);
   update each page's verified-date line.
8. `pnpm llms` — regenerate `llms.txt`/`llms-full.txt` from the updated docs.
9. `node packages/catalog-client/test/live-smoke.mjs` — pre-release gate against
   the live endpoint.

Until then, the planner's Draft tab (UCP `main`) is watch-only: pin the commit
you evaluate and keep negotiation on the dated release.
